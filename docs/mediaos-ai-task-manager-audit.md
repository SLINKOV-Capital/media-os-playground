# Аудит MediaOS для интеграции с AI Task Manager

**Дата:** 11 ноября 2026 г.
**Режим:** исследование, без изменений в коде, БД и инфраструктуре.

## Краткий вывод

MediaOS уже хранит творческие документы, их Markdown-текст, связи с материалами, рабочие действия, публикационные метаданные и дневные заметки. Основные сущности имеют UUID, временные метки и пользовательский RLS. В приложении есть защищённые Server Actions для CRUD, но нет отдельного API для ChatGPT или событийной интеграции.

Для минимального прототипа достаточно подключить ChatGPT к Supabase через существующий Supabase MCP в режиме чтения и использовать UUID MediaOS в ссылках Asana. Для записи нужен ограниченный слой команд, который вызывает бизнес-операции MediaOS с пользовательской авторизацией. Нельзя выдавать ассистенту service-role или общий прямой SQL-доступ для повседневных изменений.

## 2. Данные и назначение сущностей

### Основные таблицы

| Таблица | Назначение и ключевые поля |
|---|---|
| `documents` | Центральная сущность творческой работы: `id UUID`, `user_id`, `title`, `document_type`, `content_md`, `preview`, `created_at`, `updated_at`, `sort_order`. Здесь хранятся рассказы, статьи, книги/фрагменты, пьесы, видео и другие типы — тип задаётся текстом, а не отдельными таблицами проектов. |
| `documents` — публикация | `site_status` (`draft`/`published`), `site_slug`, `site_published_at`, `site_locale`, `site_featured`; поля аудио, YouTube и книг (`book_relationship`, `book_preview_text`, `book_preview_order`, `book_card_text`). Markdown в `content_md` — единый источник текста публикации, отдельной CMS-копии нет. |
| `materials` | Глобальные источники/атомы информации: `id UUID`, `title`, `material_type`, `file_url_or_path`, `notes` (Markdown-содержимое), `preview_url`, временные метки. Типы и ограничения валидируются приложением/БД. |
| `actions` | Внутренние действия по документу: `id UUID`, `document_id`, `title`, `done`, `today`, `sort_order`, `today_sort_order`, временные метки. Это уже рабочий чек-лист и фокус дня; срока исполнения/напоминания/зависимостей нет. |
| `nihuyasi` | Дневные заметки/идеи: `id UUID`, `date`, `text`, временные метки. |
| `daily_writing_status` | Учёт ежедневной практики, составной ключ `(user_id,date)`, `minutes` ограничены значениями 0/35/70/90. |
| `document_publication_images` | Обложки/иллюстрации публикаций; FK на документ, опциональный источник материала, роль, alt, порядок, Storage path/URL, статус. |
| `document_recommendations` | Связи рекомендаций между документами (N:M через пару ссылок). |
| `document_terms` | Термины/определения документа и необязательная ссылка на документ, где термин объяснён. |
| `document_image_issues` | Замечания к изображениям в Markdown-документе. |
| `workflow_templates_v2` | Шаблоны типов документов и стартовых названий actions, не проекты пользователя. |
| `projects`, `tasks`, `workflow_templates` | Старые таблицы v0.1. `tasks` имеет простой статус (`new`, `decision`, `stuck`, `done`, `let_go`) и необязательный `project_id`. Локальные миграции помечают их legacy/frozen; они не связаны с нынешним творческим ядром и не являются Asana-интеграцией. |

В подключённой БД также присутствует отдельная подсистема News Service (`news_*`): очередь AI-материалов, источники, публикации по платформам, интеграции и статусы. Она управляет новостной подготовкой/распространением и не должна автоматически трактоваться как проекты/действия MediaOS. `app/today/page.tsx` уже читает часть очереди News Service через отдельный service client.

### Связи и идентификаторы

```text
documents 1 ── N actions
documents N ── M materials       через document_materials
actions   N ── M materials       через action_materials
documents N ── M documents       через document_recommendations
materials 1 ── N document_publication_images (источник необязательный)
projects  1 ── N legacy tasks
```

Все основные объектные ID — UUID, пригодны как стабильные внешние ссылки. Таблицы связи имеют собственный UUID и уникальность пар. `materials.document_id` и `actions.material_id` остались deprecated для совместимости; современные связи — junction tables. Это важное ограничение при интеграции: читать корректные связи через `document_materials`/`action_materials`.

В таблицах `documents` и `actions` есть `updated_at`, который выставляется триггерами при UPDATE. Его можно применять для периодического обнаружения изменений. У junction-таблиц есть `created_at`, но нет полноценной отметки изменения/удаления родительских объектов. Удаление/отвязка не оставляет универсальный tombstone.

## 3. API и операции, уже готовые для использования

### В приложении

Server Actions уже предоставляют большой набор операций: создание/редактирование/удаление документов и материалов; обновление Markdown и preview; публикационные поля; управление actions, `done`, `today`, сортировкой; управление Nihuyasi; связи материалов и публикационные изображения. После изменений выполняются проверки текущего пользователя и `revalidatePath`.

Полезные файлы: `app/documents/actions.ts`, `app/documents/publication-metadata-actions.ts`, `app/documents/publication-image-actions.ts`, `app/nihuyasi/actions.ts`, `app/templates/actions.ts`.

Server Actions связаны с формами/внутренним UI, имеют специфичные аргументы/redirect-результаты и не являются уже готовым универсальным API для удалённого ChatGPT-клиента.

### Через Supabase MCP

Подключённый Supabase MCP умеет инспектировать таблицы и выполнять SQL; те же инструменты в принципе могут писать данные. В этом аудите использованы только list_projects/list_tables и read-only SELECT в execute_sql. Однако MCP инструмент с правами проекта может обходить RLS (привилегированный доступ), в зависимости от исполнения, и не является моделью end-user authorization. Поэтому такой инструмент подходит для прототипа и диагностики чтения с явным ограничением на SELECT; использовать его как неограниченную операционную запись из диалога небезопасно.

Публичная часть сайта уже имеет ограниченное чтение опубликованных документов и связанных публичных материалов по RLS; это не покрывает приватные черновики и не является авторизацией владельца для личного ассистента.

## 4. Авторизация, RLS и риски

- У пользовательских таблиц RLS включён. Базовые политики ограничивают CRUD строками `auth.uid() = user_id`.
- Приложение использует publishable key вместе с cookie-сессией, а пользователь извлекается через `supabase.auth.getUser()`. Это подходящий шаблон для пользовательского API: действия от имени конкретного вошедшего пользователя и RLS в базе.
- Публикационные политики разрешают anon/authenticated читать опубликованные документы и связанный контент. Для drafts должен применяться владелец/валидная пользовательская сессия.
- Некоторые junction-политики и триггеры дополнительно проверяют совпадение пользователя и допустимость связки document/action/material. Прямая запись требует правильно поддерживать эти инварианты, atomically создавать пару строк, соблюдать порядок и revalidate публикации.
- Supabase service-role ключ обходит RLS. Его нельзя передавать ChatGPT, помещать в клиент или выдавать как общий MCP credential. Хранить только серверно, если вообще нужен; предпочтительнее не вводить для этой задачи.
- Прямое SQL-изменение обходит правила предметной области в Server Actions: ограничения опубликованных документов, генерацию/проверку slug, согласованную связь и публикационные revalidation. Оно может оставить Next.js кэш устаревшим.
- Безопаснее начинать с чтения; для записи определить узкий список команд и валидацию, привязанную к user_id, с подтверждением пользователя для публикации, удаления и значимых изменений текста.

## 5. Связывание задач Asana с MediaOS

Не копировать название, статус, дедлайн и комментарии Asana в `actions` или legacy `tasks`. Asana остаётся источником истины для обязательств/сроков; MediaOS — для творческого объекта, его материалов, текста и публикации.

Минимальный вариант без схемных изменений: в задаче Asana хранить URL карточки MediaOS, например `https://app.soloten.com/documents/<document UUID>` (и при необходимости ссылку на материал `/materials/<material UUID>`). В описании задачи можно добавить маленький структурированный блок с `mediaos_document_id`, но ссылку и UUID достаточно для прототипа. Не искать объект по названию как устойчивый ключ.

Если нужен двусторонний машинный lookup и обратные ссылки из MediaOS, тогда потребуется разработать явную таблицу связей (например `asana_links` с `user_id`, `asana_task_gid`, `document_id` и/или `action_id`, URL, timestamps, уникальными ограничениями и RLS). Не расширять MediaOS копией полей задачи; синхронизировать только внешнюю идентичность и ссылку. Уточнить модель для нескольких задач на один документ и перемещения документа между пространствами.

Встроенные `actions` полезны как творческие следующие шаги по документу, но не заменяют Asana, так как у них нет дедлайнов, assignee, зависимостей, повторений и полноценной модели напоминаний.

## 6. Получение новых материалов и событий

Сейчас нет обнаруженных ChatGPT webhook, notification feed, event log, CDC consumer или Realtime подписки приложения для этих сущностей. `updated_at` позволяет polling (например, документы по `(updated_at,id)` или окна времени); для `nihuyasi` можно ориентироваться на `created_at`/`updated_at`. Поллинг может пропустить удаление, а простое окно по timestamp может повторять строки — нужен cursor и дедупликация.

Для прототипа достаточно периодически запрашивать изменённые документы и actions, а также свежие идеи. Для надёжной доставки позже добавить `mediaos_events`/outbox в той же транзакции, уникальный event ID, тип события, object ID, дату и обработанный cursor либо включить Supabase Realtime/Database Webhooks. События должны содержать минимум метаданных, а чтение полного текста — по отдельному запросу под пользовательскими правами. Нотификации ChatGPT требуют конкретного канала/клиента и не возникают автоматически из наличия MCP.

## 7. Рекомендуемая минимальная архитектура

1. **ChatGPT — интерфейс принятия решений**, не второй реестр задач.
2. **Asana — обязательства.** Для первого прототипа использовать подключение Asana в ChatGPT (если доступно в аккаунте) для чтения/создания задач и вручную/через действие сохранять ссылку на MediaOS объект.
3. **MediaOS — творческие данные.** Supabase MCP в отдельном ограниченном контексте для поиска/чтения `documents`, `actions`, `materials`, `document_materials`, `nihuyasi`; сначала только чтение. Уточнить, как MCP credential изолирует пользователя, прежде чем использовать его на приватном контенте.
4. **Операционная запись позже — небольшой набор команд.** Один узкий пользовательский API или MCP server/tool, который принимает только доменные команды (например `create_action`, `set_action_done`, `create_idea`, `update_document_preview`) и использует Supabase Auth пользователя/короткоживущие OAuth credentials. Не открывать произвольный SQL, не давать универсальный CRUD и service-role модели.
5. **Идентификаторы — ссылки.** Asana хранит URL и UUID MediaOS; текст творческой работы хранится только в MediaOS.
6. **Изменения — polling сначала, outbox/event позже.** `updated_at` хватает для начального pull; события нужны только если появилась конкретная потребность в своевременных push-уведомлениях и надёжной доставке.

### Минимальный прототип без нового интерфейса и сервера

- Оставить имеющиеся приложения/БД без изменений.
- Включить доступный для пользователя Supabase MCP и проверить, что запросы ограничены чтением, начать с опубликованных документов или отдельного тестового набора, затем после проверки доступа — приватные данные.
- Подготовить для диалога короткую карту схемы и правила: ID — ключ; MediaOS action — творческий шаг, Asana task — обязательство; по запросу ассистент находит документ, предлагает связать его Asana задачей; ссылка/UUID заносится в описание Asana вручную или существующим Asana connector.
- Раз в день/по запросу получать изменения по `updated_at` и последние `nihuyasi`; ChatGPT формирует сводку, но не рассылает/не меняет данные автоматически.
- Для write-пробы использовать ручной интерфейс MediaOS или существующий Asana connector. Прямые UPDATE через привилегированный SQL/MCP в прототип не включать.

## 8. Уже есть / требуется / не разрабатывать

| Категория | Рекомендация |
|---|---|
| Уже готово | Supabase Auth и RLS; UUID; творческие documents с Markdown и draft/published статусом; материалы и связи; actions с done/today; идеи Nihuyasi; updated_at; публичные URL карточек; CRUD через внутренние Server Actions; доступный Supabase MCP для read-only исследования. |
| Потребуется для безопасного write | Узкий endpoint/MCP tool с пользовательской идентификацией и проверками; набор разрешённых команд, согласование рискованных действий; стабильный контракт результатов и idempotency для повторов; возможно таблица external links, если ручных ссылок недостаточно. |
| Потребуется для надёжных push-событий | Outbox/event feed с tombstones и cursor либо корректно настроенный Realtime/webhook плюс потребитель/доставка; только если polling перестанет удовлетворять. |
| Категорически не стоит | Дублировать тексты, материалы и статусы задач в третьей БД/таблице; переносить Asana сроки и зависимости в `actions`; выдавать ChatGPT service-role; предоставлять агенту произвольный SQL/write-anything MCP; строить отдельный интерфейс или новый сервер до проверки полезности прототипа; разрабатывать собственный task manager вместо Asana. |

## Ограничения аудита

Схема проверена по локальным SQL-миграциям и read-only инспекции активного Supabase проекта. Данные пользовательских строк, секреты и значения `.env.local` не читались. Существование подключения Asana в конкретном аккаунте ChatGPT не подтверждено этим репозиторием; оно зависит от доступных в аккаунте коннекторов/разрешений. Актуальную конфигурацию grants и поведение подключённого MCP в отношении RLS следует отдельно проверить на минимальном тестовом ресурсе до чтения приватного контента.
