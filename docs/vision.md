# MediaOS Vision

## Что такое MediaOS

MediaOS — это личная операционная система независимого автора, редакции и издательства.

Она не создаёт контент сама.

Она помогает пройти весь путь от идеи до публикации, сохраняя знания, историю и результаты работы.

Главная цель — не автоматизировать человека, а убрать рутину, чтобы больше времени оставалось на мышление, творчество и принятие редакционных решений.

---

# Главный принцип

Любой контент проходит единый жизненный цикл:

```
Источник → Исследование → Черновик → Редактура → Медиа → Публикация → Аналитика
```

Неважно, новость это, статья, рассказ, глава книги, сценарий, видео, подкаст или презентация — **по смыслу** это один процесс.

Но в MediaOS **Новости** и **Документы** — **разные сущности**, не варианты одной таблицы.

---

# Новости vs Документы

| | Новости | Документы |
|---|---------|-----------|
| Природа | Одноразовый снаряд: опубликовал — забыл | Мини-проект: живёт, обновляется, перелинковывается |
| Редактура после публикации | Не актуализируются | Постоянно дорабатываются |
| История версий / diff | Не нужны | Нужны (поэтапно) |
| Связь с сайтом | Могут анонсировать Document или редко — целиком маленький Document | Публичный сайт (`/p/[slug]`) — основная витрина |
| Видео | Вложение к новости (ролик из сети или свой) | Отдельный Document — отдельное «большее дело» |
| Materials (Cockpit) | **Не связаны** | Глобальные materials, many-to-many с document |

**Важно:** статья про ИИ и видео про ту же тему — это **два разных Document**, а не один document в двух каналах.

**Для новостей** одна новость может уйти в Threads, LinkedIn, Telegram и т.д. — это мультипостинг **одного** news-item, а не смешение разных проектов.

Новость может **иногда** ссылаться на Document (анонс) или редко — целиком опубликовать маленький Document. Это исключение, не правило.

---

# Новости

Новости — **отдельная сущность**, не статьи блога и не `documents`.

Характеристики:

- опубликовал и не возвращаешься к правкам;
- без diff и истории версий;
- видео/картинка — **вложения к новости** (Assets), не отдельный Document.

**Сбор, редакция и публикация новостей** — в **NewsService**.

MediaOS **не публикует** новости в соцсети и **не хранит** новостной конвейер (черновики, отбор, Assets).

MediaOS показывает **аналитику публикаций из соцсетей**: просмотры, лайки, комментарии и т.п. — данные, которые NewsService собирает после постинга и передаёт в MediaOS (API или периодический sync).

### Рабочий процесс (целевой)

```
Collect → Raw Feed → AI Picks → Drafts → Publishing → Queue → Published
```

Подробности — в файле **vision.md** проекта **NewsService**

---

# Документы

Document — единица работы в Cockpit: статья, рассказ, книга, сценарий, семинар, исследование, презентация, руководство, видео, подкаст и т.д.

Документ — **мини-проект**: actions, materials, шаблоны workflow, публикация на сайт (`content_md`, `site_slug`).

Документы **перелинковываются** и **актуализируются** после публикации на сайте.

Сделать статью — одно дело. Сделать видео по той же теме — **другое**, отдельный Document.

Публичный сайт показывает опубликованные documents. Отдельной CMS и копий контента нет — MediaOS единственный источник истины.

> MediaOS является единственным местом редактирования Documents.
>
> Website никогда не редактирует контент.

---

# Materials vs Assets

## Materials (Cockpit)

Глобальные вспомогательные объекты автора: источники, ссылки, заметки, файлы.

Связаны с **Documents** через `document_materials`.

**С новостями не смешиваются.** Текст из новости можно вручную перенести в Material.

## Assets (новости)

Сущности **подготовки новости**: обложки, иллюстрации, видео к посту.

На первом этапе — **генерация обложки** по заданному алгоритму.

С Materials физически не связаны.

# Основные модули

## Sources

Сбор из RSS, Telegram, YouTube, Reddit, Hacker News, GitHub, сайтов, документов пользователя.

Задача — находить потенциально интересное, **не писать**.

Для новостного конвейера сейчас реализовано в `ai-business-news-bot`.

---

## Editorial

Редакционное ядро: отбор, черновик, переписывание, стиль, фактчек, варианты.

ИИ — помощник редактора, а не редактор.

**История изменений** — для Documents (поэтапно). Для новостей — не требуется.

---

## Publishing

### Новости (News Service)

Публикация новостей выполняется **только в News Service** — не в MediaOS.

Площадки: Threads, LinkedIn, Telegram, VK, Instagram, TenChat и др.

У каждой площадки — свои правила (длина, картинка, первый комментарий, хэштеги, ссылки, время).

Перед Publish — **экран настройки**: галочки «куда постить»; одна новость может уйти в несколько каналов.

API Threads и LinkedIn: `ai-business-news-bot` (`src/threads/publisher.py`, `services/linkedin_publisher.py`).

Секреты соцсетей — env **News Service**, не MediaOS.

### Документы (MediaOS → Website)

Публикация documents — на **сайт** (`/p/[slug]`). Соцсети для document — отдельные решения позже, без модели «один document → все каналы».

---

## Analytics

Эффективность публикаций новостей в соцсетях.

**News Service** — источник правды по новостям и posting; собирает метрики с площадок (Threads, LinkedIn, …).

**MediaOS** — **дашборд аналитики**: просмотры, лайки, комментарии, CTR, сравнение каналов. Контент новости и редакционный конвейер в MediaOS **не дублируются**.

**v1 sync в MediaOS:** идентификатор поста, канал, URL, базовые метрики на момент опроса.

**Позже:** история метрик во времени, агрегации, отчёты.

---

## Knowledge

Редакционные политики, стиль, словари, шаблоны, исследования, накопленный опыт.

Используется всеми модулями. Реализация — поэтапно (файлы, materials, отдельные сущности).

# Физическая архитектура

## Связи между приложениями

### News Service → MediaOS

News Service — **автономное приложение**: сбор, редактура, публикация, **своя база данных** (не Supabase MediaOS).

MediaOS **не переводит** News Service на Supabase. Связь — **только передача статистики публикаций** из соцсетей (просмотры, лайки, комментарии и т.п.) для дашборда.

Интеграция: API или периодический sync (News Service → MediaOS Supabase). Контент новостей и workflow остаются в News Service.

### MediaOS → Website

Website читает опубликованные Documents из общей базы данных (или через API).

Website никогда не является источником данных и не содержит собственной CMS.

## Хостинг

Website → Timeweb

MediaOS → Vercel + Supabase (documents, website, **дашборд stats новостей**)

News Service → **собственный хостинг и БД** (VPS, Vercel + SQLite/Postgres и т.д.) — **без Supabase MediaOS**

News Service может быть вынесен в отдельную инфраструктуру без изменения бизнес-логики.

---

# Принципы

- Публикация **новостей** — в **News Service**; MediaOS — **дашборд stats** (не общая БД с новостями).
- News Service **не мигрирует** на Supabase MediaOS; sync только **метрик соцсетей**.
- **Paste** для новостей — временный bootstrap, не целевой UX.
- Materials и Assets новостей — **не смешивать**.
- Один Document на сайте — один источник истины (без копий для CMS).
- Разные типы контента по одной теме (статья / видео / подкаст) — **разные Documents**.
- Все изменения Documents сохраняются — **поэтапно** (сначала новости в боте, потом полная история в Cockpit).
- Любой модуль развивается независимо.
- ИИ помогает, но не скрывает ход работы.
- Пользователь видит источник и цепочку обработки.

# После запуска сайта (backlog)

Задачи ниже — **не для текущего запуска**. Берёмся, когда публичный сайт уже в проде.

## Цитаты как вход в творчество

На сайте живёт виджет с цитатами из художественных произведений.

- Показывается одна цитата за раз.
- Каждые 5–10 секунд цитата плавно сменяется.
- При наведении анимация останавливается.
- Под цитатой отображается источник («Кузька», «Питерский ангел» и т.д.).
- Название произведения кликабельно и ведёт на полный текст.
- В виджет попадают только действительно сильные, самостоятельные фразы, способные заинтересовать читателя без знания контекста.

Цель — не демонстрация афоризмов, а знакомство посетителя с авторским стилем. Каждая цитата должна работать как приглашение прочитать произведение целиком.

## Музыка на сайте

Фоновое звуковое сопровождение публичного сайта (плейлист / атмосферные треки автора).

- Включение только по явному действию пользователя (без автоплея со звуком).
- Управление: play/pause, громкость; состояние не должно мешать чтению.
- Учитывать `prefers-reduced-motion` / доступность: музыка не обязательна для навигации.
- Контент и права на треки — решить до реализации (свои записи vs лицензии).

## Кастомный курсор

Свой курсор на публичном сайте как часть визуального языка бренда.

- Десктоп в приоритете; на тач-устройствах — системный курсор / без кастома.
- Не ломать кликабельность, hover-зоны и доступность (фокус с клавиатуры остаётся видимым).
- Лёгкая реализация (CSS / небольшой JS), без тяжёлых библиотек, если хватает.

## Motion на публичном сайте (принято)

- **Меню / ссылки «Обо мне»:** hover — лёгкая волна по буквам (`WaveText`).
- **Футер (кликабельное):** hover — переворот символов как на механическом табло (`FlipText`).
- Только при `(hover: hover)`; при `prefers-reduced-motion: reduce` — без анимации.

## Страница статьи: медиа, термины, оглавление, рекомендации (backlog)

Цель: богатая статья без перегруза (чтение — Medium-колонка ~680px).

### Раскладка (принято)

- **Desktop wide:** оглавление sticky **слева** (авто из H2/H3); текст по центру; **термины sticky справа**.
- **Mobile:** без боковых колонок; термины — по tap на подсветку в тексте (карточка).
- Над текстом — **одна светло-серая полоска**: слева иконки видео/аудио/презентация, справа EN/ES.
- Внизу — **Рекомендованные статьи**: сетка **2 колонки** как Medium (cover 16:9 → title → preview). Шире reading-колонки (~1080). Mobile — 1 колонка.
- **TOC (wide):** pin слева; `--font-ui` + `--type-quotes`; активный = ink + semibold (без оранжевой полоски).
- **Термины (wide):** pin справа; расшифровка сверху; lemma на серых плашках (`--type-quotes`); активный = префикс «→»; карточка без border; ссылка ink, accent только на hover.

### Термины (принято)

- Как Ahario: на старте до ~10, потолок ~20–30 на статью; не user-driven.
- В тексте вхождения **подсвечены нейтральным серым фоном** (не жёлтый маркер; мягкий contrast, не спорит с акцентом `#F9461D`).
- Hover/tap: **абзац-пояснение** + «Объясняется в: [название статьи]» → ссылка. Не «первые строки» статьи-объяснения.
- Генерация списка терминов — агент (рядом с перелинковкой); на сайт только после подтверждения в Cockpit.

### Видео / аудио / презентация (принято) — не Materials

Materials остаются рабочим гибким слоем Cockpit и **не** являются обязательным источником этих слотов.

| Слот | Что это |
|------|---------|
| **Видео** | Отдельный **Document** (ролик на YouTube). Статья **ссылается** на video-Document (связь Document↔Document). Согласуется с принципом: статья и видео по теме — разные Documents. |
| **Аудио** | **Свойство/артефакт статьи**, не Material: генерируется сервисом TTS, привязано к document. |
| **Презентация** | То же класс: артефакт, привязанный к document (не обязательный Material). |

Хранение URL/файлов и точная схема БД — решить отдельно; на UI статьи — опциональные слоты.

**EN / ES (принято):** поля у того же Document (`content_md_en`, `content_md_es`), не отдельные documents. Перевод ИИ — позже; на UI — переключатель, если поле заполнено.

### Рекомендации и перелинковка (предложение к утверждению)

Принцип: **на сайте только явные, подтверждённые связи**. Никакого «угадай на лету» у читателя. Агент предлагает — человек решает.

#### Две оси (не смешивать)

| Ось | Зачем | Где на сайте |
|-----|--------|----------------|
| **Related** | «Что ещё почитать после этой» | Блок внизу, Medium-grid |
| **Terms** | «Что нужно понимать» + мост к статье-объяснению | Подсветка в тексте + рейл / карточка |

Related ≠ «все статьи, где есть тот же термин». Термин ведёт в `explained_in`; related — редакционный следующий шаг.

#### Модель данных (минимум)

**`document_related`** (ordered): `from_id` → `to_id`, `position`, `source` (`manual` | `agent_accepted`).

**`terms` + `document_terms`:**
- `terms`: `lemma`, `gloss` (абзац), `explained_in_document_id`
- `document_terms`: какие термины в словаре *этой* статьи + порядок
- глосс и explained_in — **один раз на Term**, не копипаста в каждую статью

Видео статьи — отдельная Document↔Document связь (уже в духе vision).

#### Алгоритм агента (related)

При «Предложить связи» / публикации: title, preview, content, type, terms, список published.

Скоринг кандидата (черновик):
1. общие термины — сильный сигнал  
2. близость embeddings (title+preview+начало текста)  
3. общие materials/теги — если появятся  
4. тот же type — лёгкий boost  
5. штраф: уже в related, дубль, не published  

Выход: топ 5–8 + короткий why. Человек отмечает 2–4 → `document_related`.

#### Алгоритм агента (terms)

1. извлечь 8–15 lemma  
2. глосс-абзац + предложить `explained_in` (существующая статья или «нужна отдельная»)  
3. человек правит/accept → `terms` + `document_terms`  
4. на сайте подсветка только по lemma из `document_terms` этой статьи  

**Ручной путь с дня 1:** мультивыбор related + CRUD терминов в Cockpit без агента.

#### Cockpit UX

Вкладка Document **«Сайт / связи»**: related (drag-порядок) + «Предложить агентом»; terms (lemma → глосс → explained_in). Не путать с Materials.

#### На сайте

- пустой related/terms → блок не рендерится  
- только accepted / привязанные строки  

#### Этапы

1. демо / вёрстка — ручные related в коде (как сейчас)  
2. перед ~10 статьями — таблицы + ручной UI  
3. следом — агент propose/accept  
4. позже — embeddings и пересчёт предложений при правке (не авто-публикация на сайт)  

#### Не делать

- related = «все статьи с этим термином»  
- сырой вывод модели читателю без confirm  
- глосс только внутри markdown одной статьи (словарь должен переиспользоваться)

## Страницы семинаров и бизнеса + кликабельные карточки

После запуска сайта и блога: есть готовый материал для **страницы семинара** и для **страницы для бизнеса**.

- Оформить отдельные публичные страницы под этот материал.
- На главной в секции `(Семинары)` сделать **всю карточку кликабельной** (не только заголовок) — ссылка на соответствующую страницу.
- Пока сайт/блог не в проде — не реализовывать; только напоминание.

# Конечная цель

MediaOS — единая рабочая среда автора.

Не набор отдельных ботов. Не коллекция скриптов. Не CMS.

Операционная система, в которой рождается, развивается, публикуется и анализируется весь контент — с допустимым поэтапным переносом функций из существующих инструментов.
