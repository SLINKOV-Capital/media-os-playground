# MediaOS как единая система управления проектами и задачами: оценка реализуемости

**Дата аудита:** 12 ноября 2026 г.
**Режим:** исследование существующего кода и схемы; без изменений приложения, БД и инфраструктуры.

## Вывод

Сделать MediaOS рабочей системой на трёх уровнях можно с небольшим числом изменений, опираясь на существующие UUID, таблицы, Server Actions и `@dnd-kit`. В БД уже присутствует зачаток `projects → tasks`, но обе таблицы v0.1 обозначены как legacy/frozen. Современная система документов/действий независима от них: `actions.document_id` ведёт прямо к `documents`, а действий внутри task сейчас нет.

Наиболее экономичная модель — постепенно реактивировать существующие `projects`/`tasks` (после проверки legacy-данных и фактической полноты текущей схемы), расширить `tasks` явным статусом доски и плановыми полями, а `actions` связать с задачей. Документ остаётся отдельным содержательным объектом, который можно привязать к проекту/задаче ссылкой; его не нужно копировать в task. Перед принятием решения нужен ответ на вопросы в конце отчёта: прежде всего что именно обозначают пять колонок и что считать проектами текущие `documents`.

## 1. Что изучено и ограничения

Проверены Next.js App Router, компоненты списков и карточек, Server Actions, SQL-миграции, типы, документация, а также схема активного Supabase-проекта `media-os-cockpit` read-only. Наличие таблицы в старой миграции не означает, что её безопасно или удобно сразу вновь использовать: локальные docs называют `projects`, `tasks`, `workflow_templates` замороженными, а миграции содержат последующие изменения/сброс материалов. План ниже предполагает короткий инвентаризационный этап и не предлагает немедленную миграцию.

## 3. Структурные ограничения существующей модели

1. **Смешение двух смыслов слова «проект».** В legacy `projects` есть только имя и связи с tasks. Современные `documents` — проекты/произведения как контент, например рассказы или книги, с публикационным жизненным циклом. Их нельзя массово переименовать/слить в `projects`: это повредит маршрутам, сайту и редактору.
2. **Разрыв в иерархии.** Сейчас `tasks.project_id` есть, но `actions` прикреплены к документу, а не к task. Для требуемого «проект → задача → действие» не хватает `actions.task_id` (или эквивалентного FK). При этом action может оставаться видимой на document, если связи с документом нужны для текущего checklist — решение о единственном/нескольких родителях надо принять отдельно.
3. **Legacy status не соответствует доске.** `task_status` допускает `new`, `decision`, `stuck`, `done`, `let_go`; у project нет стадии. Требуемые «Идеи, Намерения, Обязательства, Проекты, Хотелки» семантически могут быть не статусами task: «Проект» — уровень иерархии, остальные могут быть состояниями идеи/обязательства. Нельзя автоматически представить их одним enum, пока не уточнена семантика.
4. **Нет планирования обязательств.** Ни у `tasks`, ни у `actions` нет `due_at`/дедлайна, времени события, часового пояса, приоритета как поля, зависимостей. Есть только ручной `sort_order`, `today`-флаг и статусы task.
5. **Текущие тексты разрознены.** `tasks.notes` есть; `projects` и `actions` не имеют описания/заметок. Для минимального интерфейса можно начать с имеющихся notes и добавить поля только двум уровням, которым их не хватает, избегая отдельной таблицы описаний.

## 4. Модель данных с минимумом изменений

### Рекомендуемый кандидат — расширить legacy основу, не создавать второй менеджер

| Уровень | Таблица-кандидат | Уже есть | Минимум, которого не хватает |
|---|---|---|---|
| Проект | `projects` | `id`, `user_id`, `name`, timestamps | `description/notes`, явное поле колонки/статуса только если проект тоже перемещается по доске; `sort_order` в пределах owner/column. |
| Задача | `tasks` | `id`, `project_id`, `title`, `status`, `notes`, timestamps | `sort_order` в пределах проекта/колонки; `due_at` (date или timestamp после уточнения), `priority` не обязательно приоритетным enum — ручной порядок как приоритет; временное событие отдельно от срока выполнения; зависимости — только после подтверждения необходимости. Нужен статус/колонка с чёткой семантикой. |
| Действие | `actions` | `id`, `document_id`, `title`, `done`, `today`, порядок | Добавить связь с task и `notes/description`; срок только если действия реально планируются отдельно. Сохранить обратную совместимость UI действий документов. |
| Документы | `documents` | полный контент, публикация, UUID | Не дублировать Markdown. Для прикрепления к карточкам можно использовать существующий `document_materials` только если материал-ссылка допустим как семантическая модель; предпочтительнее простой FK/связь document↔project/task только если подтверждена потребность. |
| Ссылки Obsidian | `materials` + `document_materials` | внешний URL `obsidian://`, тип obsidian, материал может быть связан с document | Для связей с проектом/task/action либо принять, что Obsidian-источник связан с его document и документ связан с карточкой, либо добавить общую связь после определения требований. Не копировать файл. |

**Почему не новая иерархия целиком:** `projects`/`tasks` уже имеют UUID, владельца, RLS и project FK; сортировка документов/действий показывает готовый паттерн `sort_order` + server action. Создание новых `work_projects`, `work_tasks`, `work_actions` привело бы к дублирующим реестрам и усложнило экспорт/поиск.

**Почему нельзя просто использовать нынешние `actions` как новый action-уровень:** action сегодня означает пункт checklist документа и `document_id` обязателен. Чтобы не сломать текущие документы, можно расширить её опциональным `task_id`, оставив `document_id` nullable только если доменно допустимо, или сделать отдельную таблицу-связь/новый тип. Это требует решения о том, может ли один action принадлежать одновременно task и документу. Это главный технический вопрос модели.

### Порядок и пять колонок

`sort_order` уже применён отдельно на документ и action; task/proj можно реализовать тем же способом. Для Kanban понадобятся сортировка внутри `(owner, column, parent)` и действие переноса, которое обновляет состояние и порядок обеих колонок атомарно/с валидацией ownership. Горизонтальный перенос на `@dnd-kit` можно сделать несколькими `SortableContext` под одним `DndContext`; карточки перемещаются между контейнерами, а `onDragOver/onDragEnd` управляет оптимистическим порядком. Это расширение существующей библиотеки и паттерна, новая библиотека не нужна.

## 5. Kanban и повторное использование UI

- Переиспользовать сенсоры, drag overlay, оптимистическое обновление, rollback и router refresh из `SortableDocumentsList.tsx` / `SortableActionsList.tsx`.
- Для доски нужен новый компонент доски и карточки/колонки, но drag lifecycle и библиотека уже есть.
- Вертикальная перестановка проектов/задач/действий соответствует сохранённому `sort_order`; внутри task action-list использует тот же паттерн.
- Потребуется серверная операция `move/reorder` с проверкой принадлежности всех ID одному пользователю и разрешённости перехода. Текущее `reorderDocuments`/`reorderActions` может служить образцом, но оно сортирует только один список, не переносит сущность в другую колонку.
- Открытие карточки: можно использовать существующий паттерн маршрутов `/documents/[id]` и editor components; новые страницы/формы нужны для project/task/action, если эти сущности должны иметь расширенное содержимое.
- Публикацию лучше оставить самостоятельным разделом/срезом документов. Её поля и маршруты не должны становиться колонками управления задачами. Общий «Проекты» может показывать связанный документ, сохраняя публикационный workflow отдельно.

## 6. Obsidian и связанные документы

### Что найдено

- Материал `obsidian` хранит внешний `file_url_or_path` и выводит его как кликабельный `obsidian://` URL.
- Связь документа с материалом обеспечивается `document_materials`; материал может быть связан с несколькими документами.
- В исследованном коде не найдено парсера Obsidian wikilinks (`[[Note]]`), клиентского протокола/плагина чтения vault, синхронизации файлов или списка обратных ссылок Obsidian. Импорт `DocumentMarkdownImport` предназначен для Markdown и локальных изображений/терминов, не для чтения vault и разрешения заметок.

### Следствие для карточек

Существующий механизм можно переиспользовать для сохранения и открытия Obsidian-ссылок: карточка ссылается на документ/материал по UUID, материал указывает на `obsidian://...`, содержимое заметки остаётся в vault. Но прочитать тело заметки из ChatGPT/MediaOS только по `obsidian://` URL нельзя. Для требования «включая чтение связанных документов» нужно уточнить, что именно уже называется у пользователя механизмом чтения Obsidian: возможно внешний connector или локальный плагин не в этом репозитории.

Варианты после уточнения: (а) минимальный — хранить кликабельную ссылку и вручную вставлять нужный текст; (б) существующий Obsidian MCP/connector, если он уже развёрнут, использовать для чтения по имени/путям; (в) при отсутствии — разработать интеграцию Obsidian отдельно. Не строить синхронизацию/копирование vault без подтверждённой необходимости.

## 7. Экспорт: Markdown или XML

**Рекомендация: Markdown-пакет для человека плюс машинно-читаемый manifest JSON.** Только красивый Markdown — недостаточно строгий backup: восстановление UUID/ссылок, типов, точных timestamp и зависимостей хрупко. Один JSON сохраняет типы и точные поля надёжнее, но менее удобен для чтения/переноса вручную. XML не даёт преимуществ для текущего JSON/Postgres приложения и усложняет формат.

Предлагаемый экспортный архив:

```text
mediaos-export-YYYY-MM-DD/
  manifest.json        # schema_version, exported_at, UUID и все поля/связи
  projects/<uuid>.md   # читаемая карточка, задачи и действия вложены по иерархии
  documents/<uuid>.md  # исходный content_md без переинтерпретации
  materials/<uuid>.md  # notes + type + внешний URL (в т.ч. obsidian://)
  README.md            # формат, ограничения и восстановление
```

Для полного backup в manifest включать проекты/задачи/actions, notes, колонки/статусы, due/event timestamps и timezone, `sort_order`, связи документов/materials/Obsidian, dependencies (если появятся), ID, created/updated. Не включать секреты. Публикационные документы уже в Markdown — сохранять оригинальный `content_md` без потерь отдельно, а не только отрендеренный вариант. Экспорт должен иметь версию схемы и быть проверяемо round-trip совместимым, если восстановление требуется как backup.

Сам экспортный endpoint/UI новый, но его можно реализовать без миграции: серверная функция собирает разрешённые данные текущего пользователя и формирует zip/download. Сейчас такой функции не найдено.

## 8. Планирование и календарные семантики

| Потребность | Текущее состояние | Минимальное решение после уточнения |
|---|---|---|
| Срок выполнения | Отсутствует у tasks/actions | Одно `due_at`/`due_date` на task. Выбрать date-only или timestamp; дедлайн часто date-only. |
| Приоритет | Явного уровня нет | Ручной `sort_order` внутри доски/родителя обычно достаточен. Отдельный priority enum добавлять только если нужны независимые уровни приоритета. |
| Сегодня | `actions.today` и `today_sort_order` уже работают | Для задач на сегодня добавить query/представление по due date/flag, не ломая focus actions. Определить, означает ли «Сегодня» deadline или выбранный фокус. |
| Зависимости | Не реализованы в актуальной модели; FK только структурные | Отложить. Если обязательны: минимальная self-relation `(task_id, depends_on_task_id)` с проверкой ownership, запретом цикла и экспортом. Не добавлять поле `depends_on` как произвольный текст. |
| Событие со временем | Отсутствует | Если календарное событие — нужны `starts_at`, `ends_at`, timezone/место; не смешивать с task deadline. Лучше определить event как тип task только при одинаковой модели завершения, иначе отдельный event объект/календарная интеграция. |
| Action | Сейчас чеклистный шаг | Не превращать каждый action в календарное событие; срок на action добавлять только если реальный кейс это требует. |

## 9. ChatGPT: минимальный безопасный интерфейс

### Сейчас

- CRUD Server Actions рассчитаны на UI cookie-сессию, не на независимый внешний клиент.
- Supabase RLS уже настроен для user-owned строк. Это хороший фундамент, но доступ MCP с ключом проекта может быть привилегированным и не эквивалентен пользовательской сессии; любой SQL-инструмент широкого доступа небезопасен для постоянной записи.
- `@supabase/ssr` server client использует publishable key и cookies. `middleware.ts` обеспечивает refresh сессии, не заменяет проверку полномочий каждой операции.

### Минимум для требуемых возможностей

1. Сначала read-only tool/API: поиск проекта, получение вложенных задач/actions, документов/материалов, список today; фильтр на текущего пользователя и ограничение объёма текста.
2. Затем узкие команды: create/update project/task/action, move/reorder, done, today, link document, due date и dependency (если принято). Никакого произвольного SQL.
3. Внешняя авторизация должна быть user-scoped (OAuth/короткоживущая Supabase сессия или отдельный MCP с user authorization), не service-role токен, общий для моделей. Явно подтверждать удаление, публикацию и массовое изменение содержимого.
4. Server Actions можно переиспользовать как доменную логику после выделения функций, но напрямую вызывать их из внешнего ChatGPT-клиента как контракт не следует. Добавится тонкий API/MCP adapter и валидаторы; валидация ownership/parent consistency должна оставаться серверной.
5. Сортировка и перенос должны быть атомарными с проверкой user_id; команды должны быть идемпотентными или иметь `request_id`, чтобы повторы вызова не создавали дубликаты.

| Не разрабатывать | Ещё один набор параллельных таблиц для тех же project/task; копирование документного Markdown/Obsidian файлов; собственную CMS вместо публикационных документов; отдельную систему Today при сохранении текущей; произвольный агентский SQL; календарь/напоминания/сложные зависимости до согласования семантики. |

## 11. Последовательность реализации и оценка активной работы с Codex

Оценки — часы активной разработки/проверки с Codex, не календарные сроки и не время ожидания внешних доступов. Поскольку пользователь просит сначала согласовать неоднозначности, оценки этапов после решений предварительные.

| Этап | Содержание | Оценка | Неопределённость |
|---|---|---:|---|
| 0. Модель и инвентаризация данных | Уточнить значение колонок; read-only проверить число/состояние legacy projects/tasks, версии схемы, нужен ли action→task наряду с document; описать совместимые инварианты. | 1–2 ч | Содержание legacy строк и расхождение локальных миграций с prod; внешние Obsidian средства. |

### Небольшие проверяемые релизы

1. Инвентаризация и подтверждение модели без записи изменений.
2. Reactivate data layer и CRUD только в staging/dev; существующие документы/actions проходят регрессионную проверку.
3. Внутренние страницы project/task и связи с существующими documents/actions.
4. Kanban, сначала мышь/клавиатура, затем touch; перенос и сортировка сохраняют данные после refresh.
5. Today + дедлайны; затем экспорт и восстановительная проверка на тестовых данных.
6. Read-only ChatGPT tool; после проверки пользовательской изоляции — ограниченный write набор.

## 12. Риски для работающего приложения

- **Legacy schema drift:** локальный git/documentation не является надёжным proof текущей боевой схемы. Любое использование старых таблиц требует сверить prod schema, grants, enum, policies, constraints и данные.
- **Потеря текущего checklist:** смена смысла `actions` или удаление `document_id` повредит карточки документов и `/today`. Сохранять совместимость и выполнять явную миграцию.
- **Публикационный контент:** `documents` участвуют в публичном сайте; изменение владельческой структуры, slug/type или порядка не должно менять опубликованные URL и поля.
- **Общий drag provider:** multi-container DnD легко нарушить текущую вертикальную сортировку; изолировать новую доску компонентами/ID DndContext и проверить старые списки.
- **RLS и межпользовательские связи:** таблицы связи должны проверять, что project/task/action/document/material принадлежат одному пользователю. Не полагаться только на UI.
- **Экспорт неполон:** отрендеренный Markdown теряет метаданные, а внешние Obsidian `obsidian://` ссылки не экспортируют содержимое vault. Явно документировать внешние/недоступные данные.
- **Obsidian контент:** URL-схема может лишь открыть приложение; наличие адреса не означает серверное чтение заметки. Потребуется выяснить доступы и приватность локального vault.
- **Сегодня перегружено:** `/today` уже отображает actions, writing matrix и News Service. Добавление задач требует секционирования/фильтров и не должно затрагивать очередь публикаций.
- **ChatGPT write:** привилегированный Supabase MCP или service-role может читать/менять все строки; нельзя выдавать его агенту как общий рабочий credential.

## 13. Требуются ответы до окончательного плана

1. **Что означают пять колонок?** «Идеи», «Намерения», «Обязательства» и «Хотелки» — это статусы одной карточки (обычно задачи), отдельные типы объектов, или колонки содержат смесь проектов и задач? Как перемещаемая колонка «Проекты» сочетается с обязательным уровнем Project?
2. **Как различать текущие `documents` и новые рабочие проекты?** Например, проект «Таша» может содержать рассказ-документ «Таша»; нужно ли связывать их или считать одним объектом? Могут ли задачи быть без проекта?
3. **Что такое Action после внедрения уровней?** Сохраняется ли action как checkbox внутри документа и одновременно как шаг task, либо новый Action — единый объект, а document checklist должен ссылаться на него?
4. **Какой Obsidian-механизм сейчас используется для чтения связанных документов?** Укажите имя MCP/плагина/скрипта или путь/репозиторий. В этом коде обнаружено только хранение/открытие `obsidian://` ссылок и `materials` типа `obsidian`, не чтение vault и `[[wikilinks]]`.
5. **Срок или событие:** достаточно даты дедлайна, или нужны календарные события с точным временем, длительностью и TZ? Должны ли события занимать колонку Kanban?
6. **Зависимости и backup:** нужны ли зависимости в первой версии? Экспорт должен быть только для просмотра либо должен допускать точное восстановление/импорт в MediaOS?

До ответа на эти вопросы окончательная модель переходов, схема Action и точные оценки остаются условными. Прочие части аудита и поэтапный каркас обоснованы имеющейся реализацией.
